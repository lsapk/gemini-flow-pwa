# Security remediation record

This is a source review and a set of targeted remediations. It is not a claim that every vulnerability has been found. No production migration, deployment, payment, external message, or live exploit was performed. Anthropic security-guidance and the HexstrikeAI/CyberStrikeAI projects informed the requested review scope; their presence is not evidence of a completed scanner run. Offensive frameworks were not installed or run.

## Backend findings and changes

| Finding                                                                                                                                                    | Remediation                                                                                                                                                                                                                                             | Boundary covered                                                         |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| All Gemini routes accepted a body user ID and used the service role to fetch that user's records. Enhanced chat also logged private prompts and answers.   | Each route verifies its bearer token with Supabase `getUser`, rejects mismatching legacy ID fields, loads only the verified owner's records with their token/RLS, and removes prompt/answer logs.                                                       | Unauthenticated calls, stale tokens and cross-user data access.          |
| Analysis and client quota helpers treated everyone as premium; enhanced chat bypassed the legacy quota entirely. Count-then-insert quotas were race-prone. | All three routes share service-only reservation/finalization RPCs. A transaction advisory lock serializes each user's credit reservations. Clients have read-only usage access.                                                                         | Route switching, client tampering, concurrent quota overspend.           |
| Provider failures could consume quota without a useful answer.                                                                                             | A reserved credit is refunded on timeout, provider error, blocked/empty response or parse failure. Finalization is idempotent and only changes a `reserved` row, so a succeeded credit cannot later be refunded.                                        | Failure/refund replay.                                                   |
| A browser passcode and session storage granted administrator UI status; email-based database triggers/RPCs and a public endpoint provisioned roles.        | Removed browser authority, disabled the endpoint and bootstrap RPC, removed the email bootstrap trigger, and made roles browser read-only.                                                                                                              | Client role forgery and email-based automatic privilege creation.        |
| Mobile purchase validation trusted product IDs and optional client user IDs without contacting a store.                                                    | Authenticated endpoint returns 503 and grants no entitlement until Apple/Google receipt validation, user binding and replay protection are implemented.                                                                                                 | Forged purchase claims.                                                  |
| Checkout expected `productId` while the client sent `planType`; placeholder prices and request Origin controlled payment redirects.                        | Exact server price allowlist for basic/premium/ultimate, verified user/customer binding, fixed `APP_URL` redirects, Stripe idempotency keys, and existing-subscription check.                                                                           | Price manipulation, redirect injection and accidental repeated checkout. |
| The existing signed webhook inferred entitlements from checkout metadata and did not track replay or event order.                                                                                                       | Kept raw-body Stripe signature verification and added authoritative subscription retrieval, price allowlist, user/customer binding, transactional replay records and stale-event protection. `check-subscription` trusts only verified, unexpired entitlements. | Forged/replayed events and stale cancellations.                          |
| Dynamic SECURITY DEFINER offline sync accepted arbitrary table/field/owner input and bypassed RLS.                                                         | Replaced with SECURITY INVOKER functions, exact table/field allowlists, quoted identifiers, parameterized values, ownership checks and user-scoped Edge RPC calls. Batches are bounded and atomic.                                                      | SQL injection, ownership reassignment and arbitrary-table writes.        |
| Existing role/subscriber/request grants and policies were incomplete; child references could point to another owner's records.                             | Corrective migration enables RLS on every public base table, recreates strict own-row policies on known private app tables, removes browser writes to roles/subscriptions/receipts/usage, and validates owned references by trigger.                    | Direct REST bypass and cross-owner parent references.                    |
| Generated schema types include automation-engine credential, user and workflow tables in public.                                                           | Revoke web-role grants on identified automation internals, preserving their data and database-server access.                                                                                                                                            | Accidental secret exposure through the Data API.                         |

Shared request handling now enforces POST, exact configured CORS origins, bounded streaming bodies, JSON validation and generic errors. Requests without Origin remain possible for native clients and still require authentication on protected endpoints. CORS is not authentication. AI input is bounded to 8,000 characters, history to 20 messages of 4,000 characters, provider requests to 45 seconds and output to 2,048 tokens. AI suggestions remain untrusted proposals requiring user confirmation. Existing public views are switched to PostgreSQL 15 security-invoker behavior; web access to materialized views is revoked because their stored snapshots cannot inherit row policies.

Routine productivity scores are now transparent local calculations, with no background paid AI calls on mount, analytics refresh or visibility changes. Manual advice/profile buttons state the one-credit cost and the data sent to Google Gemini. Journal and daily reflection contents are excluded server-side unless `context.include_journal` is explicitly true. The profile screen presents an unchecked, account-scoped inclusion control. AI JSON is schema-validated before rendering; malformed responses show an error rather than fabricated scores. Locally generated observations are labeled as local and do not assert psychological diagnoses or comparisons against other users.

## Credits and billing configuration

### Hosted Supabase findings

The deployed schema and advisors were inspected in read-only mode on the Leny.grivel project. Legacy policies permitted client writes to the caller's subscriber and credit rows. Legacy quota RPCs also permitted resets or invalid debit amounts, and the offline batch function accepted a caller-supplied owner. The migration replaces these paths with owner checks and a server-owned ledger. It supports both the deployed TEXT role and the older enum fixture.

Browser access to legacy Google token views and developer OAuth token tables is revoked. The old developer API, OAuth issuance, PayPal endpoints and unsupervised AI routes return an explicit unavailable response in this branch. Replace their deployed versions during rollout. The administrator directory uses a role-checked, paginated Edge Function and returns a limited set of account metadata.

The hosted advisors still report excessive email OTP expiry, disabled leaked-password protection and outstanding PostgreSQL updates. See the [rollout plan](mise-en-service.md) and [Supabase security guidance](https://supabase.com/docs/guides/platform/going-into-prod#security).

Every AI request costs one credit, shared between chat and analysis. Defaults are five credits per UTC day for free accounts, 50 for basic, 200 for premium and 500 for ultimate. The service-owned `ai_credit_plans` table controls these values. Premium is finite; it requires `subscribed`, a future `subscription_end`, and `stripe_verified_at`. Existing subscriber records are preserved but previously unverified entitlements do not grant premium until reconciled against Stripe. No credit top-up fulfillment is enabled without defined products/prices.

The read-only `get_ai_usage()` RPC returns `{ tier, is_premium, daily_limit, used, remaining, resets_at }`. All quota enforcement is on the server. `used` includes in-flight reservations; refunded failures do not count. A function crash or failed refund can leave a reserved credit charged until the next UTC reset; inspect and reconcile these records using verified provider/application logs. Do not automatically refund all old reservations because the provider may have completed a billed request.

Required server secrets/configuration:

- Supabase's `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY`; service-role keys remain server-only.
- `ALLOWED_ORIGINS`: comma-separated exact web origins, including explicit local origins when needed. No wildcard or implicit production origin.
- `APP_URL`: the canonical HTTPS application origin; HTTP is accepted only for localhost/127.0.0.1 development.
- `GEMINI_API_KEY` and `GEMINI_MODEL`: an explicitly selected model ID available to the configured Google project. Deprecated hardcoded `gemini-1.5-flash` was removed.
- `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, and `STRIPE_PRICE_BASIC`, `STRIPE_PRICE_PREMIUM`, `STRIPE_PRICE_ULTIMATE`: valid recurring subscription prices. Optional monthly and annual Premium prices use `STRIPE_PRICE_PREMIUM_MONTHLY` and `STRIPE_PRICE_PREMIUM_YEARLY`. Configure Stripe's portal separately.
- Stripe webhook events: `checkout.session.completed`, `customer.subscription.created`, `customer.subscription.updated`, and `customer.subscription.deleted`. The endpoint is `stripe-webhook`; it disables gateway JWT validation and verifies Stripe's signature itself. Protected browser endpoints retain JWT validation and verify the user inside the function.

Apply the corrective migration before deploying the updated functions or enabling the credit UI. Test and reconcile legitimate preexisting Stripe customer/subscription mappings in staging; older Stripe customers lacking the expected `metadata.user_id` require an audited repair. Duplicated preexisting Stripe customer mappings will make the new unique index fail safely and require investigation. No data is discarded to resolve duplicates.

Existing administrator role assignments are preserved. Review their provenance before rollout, particularly any role created by the old email bootstrap while email confirmation was disabled. Removing the bootstrap prevents new automatic grants but cannot establish that an earlier grant was legitimate; revoke suspicious assignments through an audited administrative database operation.

## Verification and limits

- `node --test tests/security-validation.test.mjs tests/security-ai.test.mjs tests/ai-response.test.mjs`: 17 passing tests for exact CORS matching, MIME/JSON/streaming limits, privileged history-role rejection, authentication and identity mismatch on every legacy AI route, quota denial, user-scoped context loading, journal exclusion/inclusion, provider-failure refund calls, method restrictions, AI response schemas and minute-based local scoring. External Supabase/Google calls are mocked; this verifies application decisions, not live vendor behavior.
- `node --wasm-lazy-compilation --liftoff-only --no-wasm-tier-up --test tests/security-database.test.mjs`: six passing PostgreSQL/PGlite tests for the corrective migration, RLS/grants, private credential access, role/subscription/usage write denial, foreign-parent denial, sync injection/IDOR denial, quota exhaustion, refund idempotency and signed-event fulfillment RPC replay/order rules. The Windows sandbox exhausted memory when compiling PostgreSQL/WASM; the approved run outside that sandbox passed. PGlite serializes one connection and does not prove multi-connection contention behavior. Together with the HTTP/AI suite, 23 security/AI checks pass under Node 24.
- Historical migrations assume a preexisting schema and contain unsupported `CREATE POLICY IF NOT EXISTS` statements. They are not a complete fresh database bootstrap. The fixture deliberately supplies the relevant preexisting tables before testing the new migration; it does not establish that all historical migrations replay successfully.
- Staging checks still required: run Supabase security advisors; apply against a copy of the real schema; exercise simultaneous reservations on separate PostgreSQL sessions; test actual Stripe CLI signed webhook/replay and portal/checkout flows; test Gemini success/timeout/refund with the chosen model; test Supabase auth expiry/revocation; review existing privileged functions and all policies not represented in repository migrations.
- Enabling RLS on all existing public tables can reveal applications that depended on unrestricted access. Identified automation-engine tables should ultimately live in a private schema or separate database. Unknown existing policies, storage buckets, views and remote infrastructure cannot be exhaustively assessed from repository SQL alone. Existing SECURITY DEFINER public functions lose browser execution until explicitly audited/re-granted; existing trigger functions keep trigger execution.
